## What shipped

One interface and four implementations behind `build_verifier`:

| Name | Class | Label source | Optional dep |
|---|---|---|---|
| `lexical` | `LexicalVerifier` | `verdicts.classify_claim` with the lexical scorer forced | none |
| `cross-encoder` | `CrossEncoderVerifier` | ms-marco relevance (`supported` / `unverifiable`) | `sentence-transformers` |
| `nli` | `NLIVerifier` | MNLI entailment + contradiction | `transformers` + `torch` |
| `llm-judge` | `LLMJudgeVerifier` | strict-JSON judge, one retry | none (needs a client) |

Frozen contract (`docs/agent/09_P0_INTERFACES.md` §2):

```python
@dataclass(frozen=True)
class Verdict:
    label: str        # supported | contradicted | unverifiable
    scores: list[float]
    evidence_ids: list[str]
    verifier: str

class Verifier(Protocol):
    def verdict(self, claim: str, passages: list[str]) -> Verdict: ...
```

`build_verifier("lexical" | "cross-encoder" | "nli" | "llm-judge", **kwargs)`
returns the object; an unknown name raises `ValueError`. `cross_encoder` and
`llm_judge` are accepted aliases for config files.

## Decisions that matter for the paper

- **Lexical is pinned, not incidental.** `classify_claim(claim, passages)` falls
  through to the cross-encoder when `sentence-transformers` is installed, so the
  same arm would run a different baseline on the GPU box than on CI.
  `LexicalVerifier` passes `scorer=lexical_score` explicitly; a test monkeypatches
  `verdicts._cross_encoder_scorer` to fail if it is ever probed.
- **Evidence IDs are positional.** The fixed signature carries no retrieval
  backend IDs, so those cannot be recovered after the fact. Each verdict returns
  `p0…pN` in input order, including blank slots, so a caller can map `scores`
  back to the passage list it already holds. This is what makes the record
  schema's `verdicts[].scores` auditable.
- **No evidence is an abstention.** `[]`, `[""]` and `["   "]` return
  `unverifiable` without importing a model or calling the judge. This is the
  path that keeps `trust_status=abstained_no_evidence` honest and cheap.
- **Contradiction is explicit.** Lexical uses the existing numeric/negation
  check. NLI emits `contradicted` when any passage clears the contradiction
  threshold; a single refutation blocks support. The judge must say
  `contradicted`. The cross-encoder is relevance-only and never emits it — that
  is documented on the class, not hidden.
- **Supported requires support and no contradiction.** NLI: max entailment ≥
  threshold **and** max contradiction < threshold. Judge: a `supported` label
  carrying `contradiction: true` is downgraded to `unverifiable` when
  `require_bidirectional=True` (default).
- **Judge parse failure is visible.** Malformed or unknown-label output is
  retried exactly once; a second failure returns `unverifiable` with
  `verifier="llm-judge:parse-error"`, so the record shows *why* trust abstained.
  Client exceptions are retried once and then re-raised — a dead judge must not
  silently abstain every claim. Passing no passages makes zero judge calls.
- **Lazy optional deps.** Module import is stdlib-only. `CrossEncoderVerifier`
  and `NLIVerifier` import their dependency and load the model on first use
  (`load()`), raising `VerifierUnavailable` with an install hint. Call `load()`
  in preflight to fail before a paid run. `LexicalVerifier.load()` is a no-op so
  preflight code can be uniform.

### Judge prompt and client shapes

`LLMJudgeVerifier(client, model, prompt_template=None, require_bidirectional=True)`
accepts either an OpenAI-compatible object (`client.chat.completions.create`) or
`callable(prompt) -> str`. The prompt asks for
`{"label": ..., "confidence": ..., "contradiction": ...}`; `label` and
`confidence` are required, `contradiction` is optional. A custom
`prompt_template` must contain `{claim}` and `{passages}` (validated at
construction). `_render` uses plain `str.replace`, so JSON braces in a template
need no escaping.

`agents/prompts.py:119` (`TRUST_PROMPT`) remains A's single-passage, one-word
prompt; it is not wired here. The judge prompt lives in `verifier.py` because
the interface is multi-passage and JSON-scored. Wave 3 should not edit
`prompts.py` for this.

## Integration notes for wave 3 (`orchestrator/debate.py`)

1. Add `verifier: Verifier | None = None` to `DebateRunner`; default to
   `LexicalVerifier()` in `__post_init__`/first use to keep the current
   behaviour (with the important exception below).
2. Replace the direct `classify_claim(claim, passages)` call in `_evidence_for`
   with `self.verifier.verdict(claim, passages)`. Consume `.label` for the trust
   counts and keep the full object for the record.
3. Record entry: `{"agent": i, "round": r, "claim": claim, "passages": passages,
   "scores": v.scores, "evidence_ids": v.evidence_ids, "verdict": v.label,
   "verifier": v.verifier}`. The schema calls the label `verdict`; the dataclass
   field is `label`.
4. `evidence_ids` indexes the exact `passages` list passed in. Do not re-sort or
   de-duplicate between retrieval and the verdict, or the IDs stop matching the
   evidence block shown to the agent.
5. To judge with a `VLLMClient`, wrap it:
   `LLMJudgeVerifier(client=lambda prompt: judge_client.complete(JUDGE_SYSTEM, prompt), model=...)`.
   `VLLMClient` itself is not OpenAI-compatible (it exposes `.complete`, not
   `.chat`).
6. Cost: the judge is claim-level, so a debate costs `agents × claims × rounds`
   calls. `TrustConfig.max_claims` bounds it; lexical/NLI are local.
7. Behaviour change to flag in the run manifest: the default lexical verifier
   pins the lexical scorer, whereas the old code could silently take the
   cross-encoder path on the pod. Baselines must be re-run under the pinned
   verifier, not compared to Gate 0.

## Blockers

- Human annotation (shared with WP-08) — no verifier balanced accuracy can be
  reported until 150–200 pairs are labelled by two annotators.
- Pod validation of the real `CrossEncoder` / NLI checkpoints is deferred to the
  next GPU session; the local tests use fakes only, by design.
