\chapter{Standards and Design Constraints}
This chapter documents the standards that the framework adheres to,
The constraints that have shaped its design and budgetary costs of the
Experiments; and concludes by mapping the project against the
Criteria for complex engineering problems and providing a brief summary.

\section{Compliance with the Standards}
Standards play out in three areas - the software stack, the hardware the
Framework executes upon, and the communication among components. There were
Alternative options available in each area and these alternatives are explained
Below.

\subsection{Software Standards}

Python was chosen because the LLM serving and evaluation ecosystem is concentrated in Python: Hugging Face libraries, vLLM, PyTorch, and the evaluation tools all expose Python interfaces. Java and C++ are faster, but neither has the same pre-existing support for loading and serving current LLM checkpoints. The framework is a research prototype rather than a real-time production service, so ecosystem fit matters more than raw speed. The Gate 0 environment used Python 3.12.3; the repository requires Python 3.10 or newer. Surveys of LLM-based multi-agent systems describe this design space in terms of workflow, infrastructure, and open challenges~\cite{li2024survey}; the decisions below follow that structure.

vLLM is built on PyTorch and directly supports the Qwen, Gemma, and Mistral families. TensorFlow and JAX were evaluated as alternatives; TensorFlow's LLM serving story is weaker, and JAX would require rewriting the pipeline without a clear advantage.

vLLM serves models through an OpenAI-compatible API. The orchestration code can therefore call closed APIs and locally served models without modification. PagedAttention manages KV-cache memory for concurrent requests, and the Blackwell FP8 path supplies the throughput needed for the three-agent load. Ollama is simpler to set up but slower under concurrent requests; llama.cpp runs well on CPU but does not match the GPU throughput; TGI is a close alternative, but vLLM fit the existing ecosystem and exposed the OpenAI-compatible surface.

Cross-encoders rerank passages returned by retrieval. The implementation uses a sentence-transformers cross-encoder when the optional dependency is installed; the default verdict path is lexical and does not require it. BM25 is an alternative ranker, but it scores lexical overlap rather than semantic relevance. Since the verifier must judge whether a passage supports a claim, the cross-encoder is an optional reranker, not the verdict model. The web dashboard is planned with FastAPI, and result packages are JSON objects following RFC 8259 that are validated against a schema. Codebase changes are tracked with git, and LaTeX (Overleaf) generates this document.

\subsection{Hardware Standards}

The Core and Full matrices are planned for a single 80 GB A100 PCIe spot running the 4-bit 24--27B stack: Qwen3.8-27B-AWQ-INT4, Gemma 4 26B-A4B AWQ, and Mistral 24B AWQ, at about 53.3GB of weights in total. Gate~0 ran on the 48 GB RTX A6000 development card, and the 96 GB RTX PRO 6000 Blackwell FP8 stack is retained for the N1 smoke and a small GPQA precision replication (B3, B8-no-trust, B8; 150--200 questions; one seed), not for the main matrix. Memory capacity and architecture were the key considerations. The development models (Qwen3.5-9B, Gemma 4 12B, Ministral-3-14B) run as 4-bit checkpoints on the 48GB development card. The full-size models (Qwen3.8-27B, Gemma 4 26B, Mistral Small 3.2 24B) total about 77 billion parameters. The pinned FP8 checkpoints are two FP8 models and one AWQ model, totalling 73.68GB. The offline budget check passes, but the 96 GB hardware smoke has not run, so the precision stack has not been validated on the card.

An initial alternative was the RTX A6000 80GB. It has enough memory for the 4-bit stack, but it is an Ampere card and cannot run the FP8 precision checkpoints; the default matrix card is the 80 GB A100 PCIe spot at \$0.136 per GPU-hour. The 96 GB RTX PRO 6000 Blackwell at \$0.336 per GPU-hour is the fallback if the A100 spot is unavailable; it raises the envelope to about \$1,050--1,150 and requires explicit re-approval. The H100 80GB adds cost without adding memory capacity, and the L40S at 48 GB and the consumer RTX 5090 at 32 GB do not have enough memory to hold the 24--27B trio. Thus the 80 GB A100 is the default matrix card, and the 96 GB card is kept for the precision work. To stage models prior to moving them to the GPU the host computer needs at least 64 GB of system RAM and NVMe disk storage.

\subsection{Communication Standards}

All remote communication between the framework and its components uses HTTPS. Local vLLM servers expose HTTP on the host. The model server presents an OpenAI-compatible chat-completion API endpoint that is REST-based with JSON payloads. gRPC was another option for model serving; it has lower latencies in benchmark tests, but an OpenAI-compatible surface lets the framework use closed APIs and local vLLM-served models without changing the orchestration code.

Each source of evidence is accessed through its public REST interface: PubMed E-utilities, the arXiv API, the Semantic Scholar Graph API, and OpenAlex as a fallback. Each returns JSON or XML over HTTPS; the framework handles rate limits with retries capped according to the requirements. Web sockets are not used in the P0 implementation; live dashboard updates are planned.

\section{Design Constraints}

\subsection{Economic Constraint}

The matrix is budgeted at 1,067 GPU-h planned, or 1,280 GPU-h under the gate's conservative cap, on one 80 GB A100 spot at USD 0.136 per GPU-hour. The Core run is USD 175--210 including a 20\% contingency, the pilot is USD 15--20, the 32-row Full target is USD 210, and the 36-row gold-answer alternate is USD 235. The 96 GB N1 smoke and GPQA precision replication add USD 25--40 at USD 0.336 per GPU-hour, and storage and bandwidth add USD 40--80. The confirmatory envelope is USD 500--600 with a USD 600 hard stop. Retrieval APIs are free at their public tiers; MMLU-Pro is public, while GPQA and HLE are gated and not redistributed. The code is inference-only, so no training compute is required. The main economic risk is that the 80 GB A100 spot is unavailable; running the main matrix on the 96 GB card would raise the envelope to about USD 1,050--1,150 and requires explicit re-approval.

\subsection{Environmental Constraint}

The project avoids training and uses quantized inference, which keeps the compute footprint to the rented GPU hours above. Energy use was not metered during Gate~0, so the report makes no quantitative energy claim. The main environmental cost is GPU electricity and the storage of model weights and logs. The run plan reuses the model cache and copies result packages off the host before the instance is destroyed.

\subsection{Ethical Constraint}

The framework generates answers to scientific questions and can be wrong. It is a research prototype, not a source of clinical, legal, or safety-critical advice. The injection experiment fabricates a consensus, but only inside a controlled benchmark; no human subjects are involved. Dataset licences are recorded, gated datasets are not redistributed, and the result package keeps the evidence trail so a reader can inspect why an answer was selected.

\subsection{Health and Safety Constraint}

No physical system is controlled. The relevant safety risk is that a user treats a generated scientific answer as authoritative. The design mitigates this by returning the evidence trail and by evaluating abstention on retrieval-resistant items. It does not eliminate the risk, and the report does not claim deployment readiness.

\subsection{Social Constraint}

The work targets a social problem: confident but unsupported answers can mislead users. The framework is intended to make disagreement and evidence visible rather than to hide it behind a single vote. Access is a constraint: the code and configuration are intended for open release, while gated datasets are shared as identifiers and hashes only.

\subsection{Political Constraint}

The project has no direct political constituency. Scientific misinformation is a public issue, and the framework could be used to support or contest claims. The evaluation therefore reports failure cases and does not claim that the mechanism is neutral.

\subsection{Sustainability}

The main sustainability choice is inference-only operation on quantized checkpoints, which avoids training runs. The matrix is bounded by the pre-registration, and the runner resumes instead of repeating completed questions. Longer-term use would need a cost and energy audit; that audit is not part of this report.

\subsubsection{P1: Depth of Knowledge Required}

This project required knowledge of multiple areas including machine learning, natural language processing, retrieval-augmented generation, and distributed model serving. Therefore, solving the project required specialized knowledge in these areas, such as the trust update formula through the vLLM serving layer. The coverage for P1 is based on the Washington Accord K1-K8, as detailed in Table~\ref{tab:knowledge} after P7.

\subsubsection{P2: Range of Conflicting Requirements}

P2 is covered. The project needed to meet multiple competing requirements. Accuracy competed with latency and cost. The design assumes that more rounds would strengthen the signal while increasing inference time and GPU cost; the N9 ablations test that assumption. Strong weighting would limit diversity due to trust calibration. The need to cover evidence competed with API rate limits. Therefore, the team needed to resolve these together. Round caps and simplex bounds were established, and verdicts are conservatively resolved. Thus, none of the competing needs dominate.

\subsubsection{P3: Depth of Analysis}

P3 is covered. There is no textbook solution to the problem. The design defines the executable Core controls (B3, B4-matched, B8-no-trust) and the proposed B8; MoA, iMAD, and DebUnc are related baselines, not Core arms. It also defines metrics for the failure modes: final-answer accuracy, correct-minority retention, collapse under pressure, appropriate revision, and trust calibration. The injection point adds a controlled wrong-consensus condition. The matrix is pre-registered but has not been run, so the depth of the design is what supports P3, not completed comparative results.

\subsubsection{P4: Familiarity of Issues}

P4 is covered. Multi-Agent LLM Debate is a recent research area. The most similar research appeared between 2024 and 2026, and we are not aware of a standard method for resolving sycophantic collapse in multi-agent LLM debates. At the beginning of the project, the issues were unfamiliar to the team. A review of current literature was conducted before designing the framework, as described in Chapter~2. That review is what supports the P4 assessment.

\subsubsection{P5: Extent of Applicable Codes}

P5 is covered. General software standards are applicable. JSON (RFC 8259) and HTTP over TLS are applicable. Additionally, since the framework uses an open AI compatible API, the general API standard applies. However, as previously stated, there is currently no applicable code that addresses evidence-grounded trust in LLM debates. As such, this area is only partially standardized and the framework defines its own rules for the trust score and four possible verdicts. Therefore, this combination of existing codes and new conventions make P5 "covered."

\subsubsection{P6: Extent of Stakeholder Involvement}

P6 is not covered. The project does not have any external stakeholders. The only individuals involved are the supervisor and the examiners. There is no industry partner and no community group that identifies stakeholder needs or evaluates results as part of the development process. While users who will use future scientific QA tools may benefit from this project, they do not participate in either the design or testing phases of the project. The framework was designed and tested as an Academic FYDP (Final Year Design Project); therefore, the engagement is very narrow and only within the University context. For this reason P6 is considered "not covered", while the other P points are still considered covered.

\subsubsection{P7: Interdependence}

P7 is covered. The tight interdependencies between the Confidence Gate, Orchestrator, Claim Decomposer, Retrieval Subsystem, Trust Updater and Aggregator make it a candidate for P7. This means that if there is an error in the Retrieval Subsystem, this will be reflected in both Verdicts and ultimately the Final Answer through the Trust Score. Because of these interdependencies, P7 is marked as covered; the fault-tolerance requirement is stated in Section 3.1.1.

\paragraph{K1: Natural sciences} K1 has been addressed. The framework is designed to address scientific inquiries and verify each claim by comparing it to articles on PubMed, arXiv, Semantic Scholar, and OpenAlex. Natural science questions are included in evaluation data sets. The project itself is not an outcome of a new natural science theory. The problem domain and the evidence base are still sourced from the natural science fields. This is the reason for marking K1 as covered.

\paragraph{K2: Mathematics} K2 has been addressed. The trust operator uses logit accumulation, one softmax, and a simplex projection with a floor. Probability and statistical measures are used in the evaluation, including bootstrap intervals and paired tests. Both the operator and the evaluation use the same probability framework.

\paragraph{K3: Engineering fundamentals} K3 is covered. State machines (the system's design and its failure handling) are at the heart of what we've done here. Basic engineering design is used by requirements and the confidence gate along with the orchestration logic.

\paragraph{K4: Specialist knowledge} K4 is covered. The main areas are large language models, multi-agent debate, retrieval-augmented generation (RAG), and sycophancy. These areas drive how claims are divided, how evidence is retrieved, and how trust is computed.

\paragraph{K5: Engineering methods} K5 is covered. An experimental methodology is used with controlled variables. The analysis plan specifies confidence intervals and baseline comparisons. The comparative runs are not yet complete; the evidence is the implementation, the test suite, and Gate~0.

\paragraph{K6: Computational methods} K6 is covered. Our main application tools are Python, PyTorch, vLLM (to serve the model), and FastAPI (to serve the dashboard). Sentence-transformers (to re-rank passages) and Git (for version control) complete the suite of applications.

\paragraph{K7: Codes and practices} K7 has been addressed. JSON under RFC 8259, HTTP with TLS, the OpenAI compatible API, and JSON Schema (as well as many others) were all applied as codes. Standard practices were followed regarding version control and coding style.

\paragraph{K8: Research and context} K8 has been addressed. Scientific QA (scientific questions answering) provides us with our ethical bounds on the output from AIs — literature reviews, gap analyses provide the context for our research direction.

The profile is broad rather than deep in one spot. The report applies K4 and K5
in every chapter, and K6 and K7 in the implementation, which shows the range the
problem demands.

\subsubsection{A1: Range of Resources}

A1 is covered. Three model family sources; Four Literature API's; Six team members; Rented 80 GB A100 GPU. Coordinating these resources clearly has to be part of the work. The plan in Chapter 3 assigns each task to a specific team member and tracks weeks/deliverables. That is why A1 is labeled as covered.

\subsubsection{A2: Level of Interaction}

A2 is covered. The system makes heavy use of the outside world. Each round calls three local vLLM model endpoints; each claim is routed to a two-source pair (PubMed/Semantic Scholar, arXiv/Semantic Scholar, or Semantic Scholar/OpenAlex), and there is communication to and from the rented cloud GPU. Team communication occurs via the shared repository and weekly meeting. High degree of interactivity = why A2 is labeled as covered.

\subsubsection{A3: Innovation}

A3 is not covered. The framework combines existing concepts: multi-agent debate, retrieval, and trust weighting. It creates no new device and no new theory. The contribution is the combination of claim-level external evidence with a bounded in-debate trust state and a controlled wrong-majority protocol. That combination is useful and testable, but it is not a patentable or breakthrough innovation. A3 is therefore marked as not covered.

\subsubsection{A4: Consequences for Society and Environment}

A4 is covered. The work targets a social problem: unreliable and sycophantic answers from AI systems in scientific question answering. Even though the framework is a lab prototype rather than a production-deployed product, the consequences of the problem and of the solution were both considered during design. The environmental impact was assessed qualitatively: the pre-registered matrix is 1,067--1,280 GPU-h on a single rented 80 GB A100, the project does no training, and the models run as quantized checkpoints. Energy use was not metered, so no quantitative energy claim is made. These social and environmental considerations shaped the ethical constraints and the inference-only design documented in this chapter.

\subsubsection{A5: Familiarity}

A5 is covered. Both multi-agent debate/evidence verification were uncharted territory for our team. Our literature-review phase and our baseline study that used a step-by-step implementation plan were both structured around the lack of prior experience with those areas. Only after we had studied each component sufficiently could we begin implementing each one. Lack of prior-experience with many components = why A5 is labeled as "covered".

\section{Summary}
The chapter defined the requirements for the software, hardware, and communication layers and documented the economic, environmental, ethical, and social constraints that shaped design decisions. The budget analysis shows that the pre-registered matrix is 1,067--1,280 GPU-h on the 4-bit 24--27B stack on one 80 GB A100 spot, with a Core envelope of USD 175--210, a 32-row Full target at USD 210 (36-row gold-answer alternate at USD 235), and a total confirmatory envelope of USD 500--600 under a USD 600 hard stop. The complex engineering mapping shows that six of the seven P attributes are covered, with P6 not covered because there are no external stakeholders. K1--K8 are all covered. A1--A2, A4, and A5 are covered, while A3 is not. For the program outcomes, this report covers PO1, PO2, PO4, PO10, PO11, and PO12.
